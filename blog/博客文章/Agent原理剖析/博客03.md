这种现象的背后，是一个本末倒置的学习路径：**上层概念用得很熟，但 LLM 是什么、为什么有这些限制，完全没吃透。**

- **LLM 到底是什么？** —— 不是"AI"，是"下一个 Token 预测器"，从 Token 粒度到概率模型本质

- **LLM 的三大硬伤是怎么来的？** —— 不是 bug，是架构决定的。知识截止、幻觉、无法执行，每一个都是 Transformer 的必然结果
- **上下文窗口为什么是核心瓶颈？** —— O(n²) 的计算复杂度，以及它如何催生了 RAG 和记忆管理
- **这些硬伤如何催生了后续所有 AI Agent 技术？** —— 从 LLM 到 Agent 的"打补丁全景图"，理解 Prompt Engineering、RAG、Tool Use 为什么是必然产物

## 一、LLM 的本质：不是"会说话的 AI"，是"下一个 Token 预测器"

### 1.1 先定义：LLM 到底是什么？

很多人把 LLM 想象成"一个会思考的 AI 大脑"。但**技术上，LLM 做的事只有一件**：

> **根据上文，预测下一个最可能出现的 Token。**

就这么简单。你给它一段文本，它输出一个 Token；然后把这个 Token 拼到文本末尾，再预测下一个 Token；如此循环，直到生成结束。

**它没有"思考"、没有"理解"、没有"意图"——它只是在做概率计算。**

从代码层面看，LLM 的每一次调用本质上就是一次"输入文本 → 输出下一个 Token"的推理：

```python
# LLM 的本质：输入一段文本，预测下一个 Token
from openai import OpenAI

client = OpenAI()
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "中国的首都是"}]
)
# 模型输出：北京
# 然后是下一个 Token：市
# 然后是下一个 Token：。
# 如此循环，直到遇到结束标记
print(response.choices[0].message.content)
# 输出：北京。
```

**每一次输出，都是基于"上文所有内容"做一次概率计算。** 它没有"记住"之前说过什么，它只是把整个对话历史重新读一遍，然后预测下一个 Token。

### 1.2 Token：LLM 的"最小认知单位"

LLM 不是按"字"或"词"来理解文本的，它按 **Token** 来处理一切。

| 概念 | 说明 |
|------|------|
| **Token 是什么** | 文本被切分后的最小处理单元 |
| **中文** | 1 个汉字 ≈ 1-2 个 Token |
| **英文** | 1 个单词 ≈ 1-3 个 Token |
| **粗略换算** | 1000 个汉字 ≈ 700 个 Token |

**Token 是 LLM 世界里的"原子"**：

- 模型的输入输出都按 Token 计算
- API 调用按 Token 计费
- 上下文窗口大小按 Token 衡量
- 模型训练的目标就是"预测下一个 Token"

> 不理解 Token，就不可能理解 LLM 的计费、上下文、性能瓶颈。

实际用代码感受一下 Token 的切分方式：

```python
# 使用 tiktoken 查看文本被切分成了多少个 Token
import tiktoken

encoder = tiktoken.encoding_for_model("gpt-4o")
text = "人工智能正在改变世界"

tokens = encoder.encode(text)
print(f"文本：{text}")
print(f"Token 数量：{len(tokens)}")
print(f"Token IDs：{tokens}")
# 输出：
# 文本：人工智能正在改变世界
# Token 数量：5
# Token IDs：[...]
```

**同一个模型，不同语言、不同内容的 Token 消耗差异很大**——一段英文"Hello"可能只需要 1 个 Token，而中文"人工智能"可能需要 2 个 Token。这是 API 调用成本计算的基础。

### 1.3 为什么是"概率模型"而非"确定性系统"？

这和传统编程有个根本区别：

| 维度 | 传统编程 | LLM |
|------|----------|-----|
| **执行方式** | 代码逻辑确定，输入 A 永远输出 B | 概率计算，输入 A 可能输出 B、C、D |
| **正确性** | 编译器保证语法正确 | **没有"正确"的概念**，只有"概率高" |
| **调试方式** | 打断点、看堆栈 | 改 Prompt、调参数 |
| **可预测性** | 100% 确定 | **概率性** |

**这个"概率性"是 LLM 一切问题的根源**：

- 它有时输出正确答案（概率高）
- 它有时输出错误答案但看起来像真的（概率也不低）
- 它无法判断自己是对是错（没有"对错"概念）
- 同一个问题问两次，可能得到不同答案

> **LLM 的本质矛盾**：它看起来像在"理解"，但底层只是在做"概率匹配"。这个矛盾，就是后面所有工程概念（Prompt Engineering、RAG、Agent）存在的根本原因。

用一个简单的例子来感受 LLM 的"概率性"：

```python
# 同样的问题，temperature 不同，答案可能完全不同
from openai import OpenAI

client = OpenAI()

def ask(prompt, temperature):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        temperature=temperature  # 0 = 最稳定，1 = 最发散
    ).choices[0].message.content

# 同一个问题问两次，temperature=0.9 时可能得到不同答案
print(ask("用一句话描述什么是编程", temperature=0.9))
print(ask("用一句话描述什么是编程", temperature=0.9))
# 两次输出可能完全不同
```

**temperature 参数就是控制 LLM "概率性"最直接的开关**——设为 0 时模型选择概率最高的 Token（最稳定），设为 1 时模型在候选 Token 中随机采样（最发散）。

### 1.4 Transformer：LLM 的底层架构

前面讲了 LLM "做什么"（预测下一个 Token），但还有一个关键问题没回答：**它是"怎么"做到的？**

所有现代 LLM（GPT、Claude、DeepSeek、Gemini……）的底层架构都是同一个东西：**Transformer**。

#### 为什么 Transformer 是革命性的？

在 Transformer 出现之前，处理文本的主流架构是 RNN（循环神经网络）和 LSTM。它们有一个致命缺陷：

| 架构 | 处理方式 | 致命问题 |
|------|---------|----------|
| **RNN / LSTM** | 逐字串行处理，"读完第一个字才能读第二个字" | 无法并行训练，长文本会"遗忘"开头 |
| **Transformer** | 所有字同时处理，每个字都能直接"看到"其他所有字 | —— |

**Transformer 的核心创新**：**Self-Attention（自注意力机制）**。

#### Self-Attention：让每个词都能"看到"整句话

举个例子，这句话：

> "**张三把李四打了，因为他很生气。**"

问题：**"他"指的是谁？** 张三还是李四？

- RNN 读到"他"的时候，只能靠"记忆"回忆前面的内容，**容易忘**
- Transformer 的 Self-Attention 让"他"这个字**直接和前面所有字做关联计算**——"他"和"张三"的关联度 0.9，"他"和"李四"的关联度 0.1 → **判断"他"指的是张三**

```text
Self-Attention 的核心操作：
  每个词 × 其他所有词 → 计算"关联权重" → 加权融合 → 得到"理解了这个上下文的表示"

"他" ← 和张三（关联度 0.9）+ 和李四（关联度 0.1）+ 和"打了"（关联度 0.6）+ ...
```

**这就是 LLM "理解"上下文的本质**：不是真的"理解"，而是通过大量计算，**给每个词找到它最应该关注的上下文词**。

#### 为什么这决定了 LLM 的三大硬伤？

理解了 Self-Attention，再来理解 LLM 的局限就容易多了：

| 局限 | 和 Transformer 的关系 |
|------|----------------------|
| **上下文窗口有限** | Self-Attention 的计算量是 **O(n²)**——上下文翻倍，计算量翻四倍。所以上下文窗口不能无限大 |
| **知识截止** | Transformer 只是"处理输入文本"，**没有内置的"学习新知识"能力**。训练完后参数固定 |
| **幻觉** | Self-Attention 找到的是"相关性最高的上文"，不是"事实"。**如果上文没有正确答案，它就会编一个"相关性最高"的答案** |

> **Transformer 架构决定了 LLM 的能力上限和局限下限**——理解了它，三大硬伤就不再是"玄学"，而是工程上的必然取舍。

有了这个底层认知，我们再来看 LLM 的三大硬伤——**每一个都不是"没做好"，而是 Transformer 架构的必然结果**。

### 1.5 训练三阶段：从"知识渊博"到"能听懂人话"

理解了 Transformer 架构，下一个问题是：**LLM 是怎么从"只会预测下一个词"变成"能回答问题"的？**

答案是一套三阶段的训练流程：

```
Pre-training（预训练） → SFT（监督微调） → RLHF（人类反馈强化学习）
```

| 阶段 | 做什么 | 输入数据 | 产出 | 通俗类比 |
|------|-------|---------|------|----------|
| **① Pre-training** | 在海量文本上做"下一个词预测"，学习语言规律和世界知识 | 互联网文本（TB 级） | **基础模型**，知识丰富但不听话 | 刚毕业的学霸：知识渊博，但不会按你的要求回答问题 |
| **② SFT** | 用高质量"问题-答案"对微调，让模型学会遵循指令 | 人工标注的问答对（万级） | **指令模型**，能听懂人话 | 学霸经过入职培训，学会按规范回答问题 |
| **③ RLHF** | 通过人类偏好排序，让模型学会输出"更符合人类期望"的回答 | 人类对多个回答的偏好排序 | **对齐模型**，价值观对齐 | 学霸经过绩效考核，知道什么该说什么不该说 |

**为什么 SFT 之后还需要 RLHF？**

SFT 只能让模型**模仿**标注数据，但无法学会"什么回答更好"。RLHF 通过人类偏好排序，让模型学会了"好 vs 更好"的区分能力。

> **核心认知**：SFT = 教模型"标准答案是什么"，RLHF = 教模型"怎么判断答案质量"。两者叠加，模型才从"知识库"变成了"助手"。

**为什么理解训练流程对"剖析"LLM 至关重要？**

三个训练阶段，每一个都在解决上一个阶段的问题，但每一个也都在引入新的局限性：

1. **Pre-training 阶段决定了 LLM 的知识边界**：模型在预训练中"见过"什么，决定了它"知道"什么。训练数据截止之后的信息，模型不可能知道——这就是"知识截止"硬伤的根源。**不是模型不想知道，是它根本没学过。**

2. **SFT 阶段决定了 LLM 的"听话程度"**：如果不经过 SFT，Base Model 只会做"续写"，不会"回答问题"。SFT 让模型学会了遵循指令的格式，但同时也让模型学会了"编造答案"——当标注数据中有不确定的答案时，模型学到了"不确定也要编一个"的模式。**这就是"幻觉"在训练层面的成因之一。**

3. **RLHF 阶段决定了 LLM 的"安全边界"**：RLHF 通过人类偏好教会模型"什么回答更好"，但人类偏好本身就是有偏见的。模型在 RLHF 后可能变得"过度谨慎"——拒绝回答一些本可以回答的问题。**这解释了为什么不同厂商的模型（GPT vs Claude vs DeepSeek）在回答同一问题时风格差异巨大：它们经历了不同的人类偏好训练。**

> **剖析视角**：理解了三阶段训练流程，你就知道 LLM 的"性格"是怎么来的，以及为什么"调 Prompt"能改变 LLM 的行为——因为 Prompt 本质上是在"引导模型走向训练数据中某种特定的回答模式"。**LLM 不是"有思想"，而是"被训练出了某种行为模式"。**

### 1.6 采样策略：模型怎么"选择"下一个词？

前面讲了 LLM "预测下一个 Token"，但还有一个关键细节：**预测出来的是概率分布，不是确定的词。** 模型需要一套"采样策略"来从概率分布中选出最终的词。

```
模型输出分数（Logits）→ Softmax 转成概率 → 采样策略 → 选出下一个词
```

**Temperature（温度系数）**：缩放概率差距，控制输出随机性。

| Temperature 值 | 效果 | 适用场景 |
|---------------|------|----------|
| 0.1 ~ 0.3 | 高分词概率被放大，输出稳定、严谨 | 代码生成、数学计算、翻译 |
| 0.7 ~ 1.0 | 各词概率趋于平均，输出发散、创意强 | 创意写作、头脑风暴 |
| > 1.0 | 输出过于随机，基本不可用 | 不建议 |

**Top-P（核采样）**：从概率最高的词开始累加，直到累计概率达到阈值 P，截断剩余所有低概率长尾词。

| Top-P 值 | 效果 |
|----------|------|
| 0.1 | 只保留头部高分词，输出极度稳定 |
| 0.9 | 纳入更多备选词，输出多样性提升 |

**Temperature 和 Top-P 的关系**：官方建议**二选一调整**，不要同时大幅修改两个参数——两者叠加会产生不可预期的效果。

**Top-K 采样**：只从概率最高的 K 个词中采样。Top-P 更灵活（动态截断），现在主流框架默认用 Top-P，Top-K 已较少单独使用。

> 采样策略直接决定了 LLM 是"稳定可靠"还是"充满创意"——**工程上根据任务类型选择合适的参数，是把 LLM 用好的基本功。**

**为什么采样策略是理解 LLM 局限性的关键？**

采样策略揭示了 LLM 一个根本性的矛盾：**模型的"创造力"和"可靠性"是同一根轴上的两端。**

- **低 Temperature（稳定）**→ 模型倾向选概率最高的 Token → 输出可靠但缺乏多样性 → **适合代码生成、数学计算等确定性任务**
- **高 Temperature（发散）**→ 模型在候选 Token 中随机采样 → 输出有创意但可能偏离事实 → **适合创意写作，但必须警惕幻觉风险**

这个矛盾直接解释了为什么"降低 Temperature"是治理幻觉的有效手段——**幻觉的本质是模型在概率分布中选了一个"看起来合理但不符合事实"的 Token，降低 Temperature 就是让模型更倾向于选"高频正确"的 Token**。

> **剖析视角**：理解采样策略，你就理解了 LLM 为什么"同一个问题能给出不同答案"——不是因为它在"思考"，而是因为它在"掷骰子"。Temperature 和 Top-P 就是控制这个骰子"有几面"的旋钮。工程上，**选对采样参数 = 在"可靠性"和"多样性"之间找到最优平衡点**。这个平衡点，直接决定了你的 LLM 应用是"生产可用"还是"演示玩具"。

## 二、LLM 的三大硬伤：不是 bug，是架构决定的

理解了 LLM 的"概率预测器"本质，再来理解它的三个硬伤就很容易了。

### 2.1 硬伤一：知识截止（Knowledge Cutoff）

**表现**：LLM 的知识停留在训练数据截止的那一天。

| 问题 | 实际后果 |
|------|----------|
| "昨天股市怎么样？" | 编造数据 |
| "最新的 Python 版本是什么？" | 可能说一个旧版本 |
| "2026 年世界杯冠军是谁？" | 要么不知道，要么编 |

**为什么是架构决定的？**

LLM 的"知识"来自训练数据。训练完成后，模型参数就固定了——它**不会自己上网、不会自己更新**。你每次和它对话，它只是在用训练时学到的"模式"来生成回答。

> 这个硬伤**直接催生了 RAG（检索增强生成）**——给 LLM 外接一个知识库，让它能"查资料"而不是"凭记忆"。

### 2.2 硬伤二：幻觉（Hallucination）

**表现**：LLM 一本正经地胡说八道——编造人名、数据、API、论文引用。

**为什么是架构决定的？**

回到 LLM 的本质：**预测下一个 Token**。它没有"对错"的概念，只有"这个 Token 出现的概率高不高"。

当你问它一个它不知道的问题时，**它不会说"我不知道"**——因为"我不知道"在训练数据中出现的概率，远低于"编一个看起来很合理的答案"。

**关键理解**：幻觉不是 LLM 偶尔犯的错，**是它的默认行为**。LLM 的"诚实"是被训练数据中的"我不知道"例子强行塑造出来的，不是天生的。

**幻觉的四大根因**：

| 原因 | 说明 |
|------|------|
| **数据偏差** | 训练数据中本身就包含错误信息，模型学到了错误知识 |
| **知识边界** | 模型不知道训练数据截止日期后的事情，但会"编"一个答案 |
| **概率采样** | 低概率词被选中，产生不合理输出 |
| **过度泛化** | 模型把不熟悉的领域强行套用已知模式 |

**六大治理手段**（按效果排序）：

| 手段 | 说明 |
|------|------|
| **① RAG 检索增强** | 从知识库召回事实依据，注入上下文(效果最好) |
| **② 降低 Temperature** | 减少随机性，让模型倾向选最高概率词 |
| **③ ReAct 循环验证** | 每步工具调用都有事实依据，不是凭空生成 |
| **④ 结构化输出约束** | 强制输出 JSON，限定输出范围 |
| **⑤ System Prompt 约束** | 明确告知"不知道就说不知道" |
| **⑥ 多模型投票** | 多个模型分别生成，取一致结果(成本高) |

> 这个硬伤**直接催生了 RAG 和结构化输出**——用外部知识约束 LLM 的回答，用格式限制 LLM 的"编造空间"。

### 2.3 硬伤三：无法执行（No Execution）

**表现**：LLM 只会"说"，不会"做"。

| 你让它做的事 | LLM 的实际行为 |
|-------------|---------------|
| "帮我算 12345 × 67890" | 可能算错（数学推理不可靠） |
| "帮我查一下今天的天气" | 编一个天气给你 |
| "帮我把这个文件重命名" | 告诉你"应该用 `mv` 命令"，但**不会自己执行** |

**为什么是架构决定的？**

LLM 的输入和输出都是**文本**。它没有"手"去操作文件系统、没有"眼睛"去看网页、没有"耳朵"去听声音。它是一个**纯文本的输入输出系统**。

> 这个硬伤**直接催生了 Tool Use（工具调用）**——给 LLM 接上外部工具，让它能"动手"而不只是"动嘴"。

---

## 三、Context Window：LLM 的"工作记忆"及其边界

### 3.1 什么是上下文窗口？

LLM 在处理你的每一次对话时，**不是只记住你最后一句**，而是把你和它之间的**所有对话历史**都"看"一遍，然后预测下一个 Token。

它能同时"看到"的文本总长度，就是**上下文窗口（Context Window）**。

**类比**：LLM 的上下文窗口就像一块**黑板**——你每次写新内容，旧内容就可能被擦掉。

### 3.2 为什么上下文窗口有限？

**技术原因**：LLM 的注意力计算复杂度是 **O(n²)**。上下文长度翻倍，计算量翻四倍。

**现实后果**：

| 问题 | 表现 |
|------|------|
| **对话失忆** | 聊久了，LLM 忘记前面说过的要求 |
| **信息丢失** | 长文档放进去，中间部分被"忽略" |
| **成本飙升** | 上下文越长，每次调用的 Token 费用越高 |

### 3.3 上下文窗口的限制催生了什么？

> **长上下文 ≠ 有效上下文**。即使模型支持 200K Token，把一本小说扔进去，模型也未必能"记住"所有细节。

这个限制催生了：

- **RAG**：不把所有资料塞进上下文，而是**按需检索相关片段**
- **记忆剪枝**：压缩历史对话，只保留关键信息
- **滑动窗口**：只保留最近 N 轮对话

## 四、从 LLM 到 Agent：一张思维导图看懂全部因果链

![LLM 局限到 Agent 技术的因果全景图](03.png)

现在，我们把前面分析的所有内容串起来，看看 LLM 的每一个局限，是如何催生出对应的技术方案的。

### 4.1 因果全景图：LLM 的局限 → 催生的技术

在前面二、三章中，我们逐一分析了 LLM 的三大硬伤和上下文窗口瓶颈。现在把它们放在一张全景图中：

![LLM 局限到 Agent 技术的因果全景图](Mermaid%20(2).png)

**关键理解**：这不是一个"先有 LLM，然后有人发明了这些技术来补 LLM"的线性叙事。实际情况是：**LLM 的局限在工程实践中不断暴露，工程师们针对每一个局限，逐一找到了应对方案**。这些方案叠在一起，最终形成了 Agent 这个"增强版 LLM"的工程架构。

### 4.2 逐一拆解：每个"补丁"在补什么？

| LLM 的维度 | 具体限制 | 为什么需要"补" | 催生的技术 | 补丁的原理 |
|-----------|---------|---------------|-----------|-----------|
| **本质** | 概率预测器，没有"对错"概念 | 模型不知道"正确答案"是什么，它只知道"概率最高的 Token 是什么" | **Prompt Engineering** | 用精心设计的指令，把模型的概率分布"引导"到正确的方向 |
| **知识** | 训练数据截止，不会更新 | 问"昨天的新闻"，模型只能编——它训练数据里没有 | **RAG（检索增强生成）** | 不靠模型"记忆"，而是让模型"查资料"——从外部知识库检索相关文档，注入上下文 |
| **可靠性** | 幻觉，编造内容 | 模型遇到不确定的问题时，倾向编一个"看起来合理"的答案，而非说"不知道" | **RAG + 结构化输出** | RAG 提供事实依据，结构化输出（JSON Schema）限定输出格式和范围，减少"编造空间" |
| **能力** | 只会说不会做 | 模型输入输出都是文本，没有"手"去操作文件、调接口、跑命令 | **Tool Use（工具调用）** | 给模型外接"手"——定义 Tool 的 JSON Schema，模型选 Tool → 后端执行 → 结果回传 |
| **记忆** | 上下文窗口有限 | 对话长了会"失忆"，长文档中间部分被忽略 | **记忆系统（短期+长期）+ RAG** | 短期记忆：上下文窗口；长期记忆：持久化存储 + 向量检索；RAG：按需检索，不占上下文 |
| **自主性** | 不会规划、不会反思 | 复杂任务需要多步执行，模型一次只能输出一个回答 | **Planning（规划能力）+ ReAct** | 让模型"思考→行动→观察→再思考"，循环执行直到任务完成 |

### 4.3 从"补丁"到"架构"：Agent 的诞生

当上面这些"补丁"被打得足够多、足够系统化之后，一个全新的工程架构就出现了——**AI Agent（智能体）**。

> **Agent = LLM + 记忆 + 规划 + 工具调用**

这个公式的每一部分，都对应着 LLM 的一个被"补"上的局限：

| Agent 组件 | 补的是 LLM 的哪个局限 | 核心能力 |
|-----------|---------------------|---------|
| **LLM（大脑）** | —— | 理解、推理、生成 |
| **记忆（Memory）** | 上下文窗口有限 + 知识截止 | 短期记忆（上下文窗口）+ 长期记忆（持久化 + 向量检索） |
| **规划（Planning）** | 不会规划、不会反思 | 任务拆解、ReAct 循环、自我纠错 |
| **工具调用（Tool Use）** | 无法执行 | 让 LLM 能"动手"——调 API、操作文件、执行命令 |

**Agent 不是一种新技术，而是给 LLM 打了 5 个补丁之后，让它能自主完成任务的工程架构。**

### 4.4 为什么这个视角很重要？

很多人在学 AI Agent 时，路径是反的——先学 Agent 框架，再学 Tool Use，最后才回头补 LLM 基础。结果就是：**知道 Agent 怎么搭，但不知道 Agent 为什么需要这些组件。**

正确的学习路径应该是：

```
LLM 本质 → LLM 的局限 → 每个局限催生了什么技术 → 这些技术组合成 Agent
```

**理解了这个因果链，你就掌握了整个 AI 工程体系的"第一性原理"**：

- 遇到幻觉问题 → 知道是 RAG 的应用场景
- 需要模型执行操作 → 知道应该设计 Tool Use
- 上下文不够用 → 知道应该做记忆管理或引入 RAG
- 复杂任务做不好 → 知道应该引入 Planning 和 ReAct 循环

> **Agent 不是空中楼阁，它是 LLM 局限性的必然产物。理解了 LLM 的局限，你就理解了 Agent 的设计动机。**

## 五、核心要点速查

读完本文后，把最关键的 7 个核心要点浓缩在这里：

**要点 1：LLM 的本质是什么？**

> LLM 本质是**"下一个 Token 预测器"**。它没有思考、没有理解、没有意图——它只是在做概率计算。Token 是 LLM 世界的"原子"，所有输入输出、计费、上下文的单位都是 Token。

**要点 2：Transformer 架构为什么是革命性的？**

> 所有现代 LLM 都基于 Transformer。核心创新是 **Self-Attention（自注意力机制）**——让每个词都能直接和全文所有词做关联计算，不再像 RNN 那样逐字串行处理。但这个架构也带来了 O(n²) 的计算瓶颈，直接决定了上下文窗口不能无限大。

**要点 3：LLM 是怎么训练出来的？**

> 三个阶段：**Pre-training**（海量文本上学预测下一个词，产出知识渊博的 Base Model）→ **SFT**（用问答对微调，学会遵循指令）→ **RLHF**（人类偏好排序，学会"好回答"的标准）。SFT 教"标准答案"，RLHF 教"判断质量"。

**要点 4：采样策略怎么选？**

> Temperature 控制随机性（低=稳定，高=发散），Top-P 截断低概率词。**官方建议二选一调整**，不要同时大幅修改。代码生成/数学计算用低 Temperature，创意写作用高 Temperature。

**要点 5：LLM 的三大硬伤是什么？如何治理幻觉？**

> 知识截止、幻觉、无法执行——都是 Transformer 架构的必然结果。幻觉治理按效果排序：RAG > ReAct 循环验证 > 降低 Temperature > 多模型投票 > 结构化输出 > System Prompt 约束。

**要点 6：上下文窗口为什么重要？**

> Self-Attention 的计算量是 O(n²)，窗口不能无限大。长上下文时模型对中间部分注意力衰减（"Lost in the Middle"）。这个限制催生了 RAG 和记忆管理技术。

**要点 7：LLM 的硬伤如何催生了 Agent？**

> Agent = LLM + 记忆（补上下文窗口不足）+ 规划（补自主决策）+ 工具调用（补无法执行）。**Agent 不是新技术，是给 LLM 打补丁的工程架构。**

## 六、写在最后

理解 LLM 的本质，是理解整个 AI 工程体系的第一把钥匙。

很多人学 AI 工程的路径是反的——先学 Agent，再学 Tool Use，最后才回头补 LLM 基础。结果就是：**知道 Agent 怎么搭，但不知道 Agent 为什么需要这些组件。**

把 LLM 吃透之后，再去看 Prompt Engineering、RAG、Tool Use 这些概念，你会发现——**每一个概念的出现，都是为了解决 LLM 的某一个局限**。这就是后续深入学习的逻辑线索。
