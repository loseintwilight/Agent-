# RAG 检索增强生成深度剖析：从分片到向量检索，LLM 的知识缺口是怎么被补上的？

## 前言：RAG 是整个 AI 工程体系的"知识补给站"

在 LLM 深度剖析一文中，我们将 LLM 的三大硬伤归纳为：**知识截止、幻觉、无法执行**。其中前两个硬伤——知识截止和幻觉——有一个共同的缓解手段：**让 LLM 不要"凭记忆"回答问题，而是"查资料"之后再回答。**

这个解法的工程化实现，就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**。

但 RAG 远不止"查一下资料再回答"这么简单。当你真正落地 RAG 的时候，会面临一系列工程问题：

- 文档怎么切分？按段落切还是按语义切？切多大？
- 怎么把文本变成向量？为什么语义相近的文本向量也相近？
- 从 100 万条文档里找到最相关的 3 条，怎么做到毫秒级？
- 召回回来的文档质量不好怎么办？怎么兜底？

这篇文章从 RAG 的**设计动机**出发，从以下几个核心维度系统展开：

- **RAG 为什么存在？** —— LLM 的知识截止和幻觉是架构决定的，RAG 是这两个硬伤的工程解
- **RAG 的离线阶段怎么设计？** —— 分片策略、Embedding 原理、向量数据库选型
- **RAG 的在线阶段怎么设计？** —— 召回 → 重排 → 生成，每一步的工程细节
- **进阶 RAG 技术怎么演进？** —— HyDE、Self-RAG、CRAG、Graph RAG 各自解决了什么新问题
- **RAG 在真实项目中怎么落地？** —— 以企业知识库问答为案例，深度剖析完整落地链路与工程决策

读完你会明白：**RAG 不是"一个技术"，而是一套"让 LLM 从外部知识库中精准获取信息"的工程体系。** 每一层设计都是在解决一个具体的工程问题，理解了这些，你就能在项目中把 RAG 的底层逻辑讲得清清楚楚。

## 一、RAG 的本质：不是"搜索"，是"检索 + 增强 + 生成"

### 1.1 RAG 解决的核心痛点

LLM 的"知识"来自训练数据。训练完成后，参数就固定了。这导致两个不可逾越的问题：

| 痛点                 | 表现                           | 一个你能感知的例子                            |
| -------------------- | ------------------------------ | --------------------------------------------- |
| **知识截止**         | 训练数据截止后的事，LLM 不知道 | 问"2026 年诺贝尔物理学奖得主是谁"→ 编造       |
| **幻觉**             | 遇到不确定的问题，LLM 编造答案 | 问"xx 公司内部最新政策是什么"→ 铺天盖地编一套 |
| **上下文窗口限制**   | 超长文档无法全部放入           | 100 页的产品手册，只能读前 10 页              |
| **私有数据无法注入** | 企业数据不能用于训练           | 公司的内部知识库，LLM 从未见过                |

**RAG 的解法是一个朴素的思想**：**不给 LLM 塞"记忆"，而是给 LLM 配一个"搜索引擎"——问问题的时候先搜一下，把搜到的资料喂给 LLM 参考。**

```text
没有 RAG 时：
  用户提问 → LLM（凭记忆回答）→ 可能编造

有了 RAG 后：
  用户提问 → 检索知识库 → 找到相关文档 → 注入 LLM 上下文 → LLM（基于文档回答）
```

> **关键认知：RAG 只能缓解幻觉，不能根除幻觉。** 即使上了 RAG，依然存在两种典型的残余幻觉：
>
> ① **内在幻觉**：检索到了正确文档，但 LLM 在生成时曲解、篡改文档内容——比如文档写"单次导入上限 10000 条"，LLM 输出成"单次可导入 50000 条"；
>
> ② **外源幻觉**：召回了不相关或错误的文档，模型强行利用这些错误素材生成答案。
>
> 很多新手容易形成误区——以为上了 RAG 就没有幻觉了。正确的认知是：**RAG 把幻觉率从 ~30% 降到 ~5%，但残余的 5% 依然需要引用溯源、兜底策略、人工校验等机制来兜底。**

### 1.2 RAG 的完整公式

RAG 不是单个技术，而是三个环节的工程组合：

> **RAG = Retrieval（检索）+ Augmentation（增强）+ Generation（生成）**

| 环节                     | 做什么                                               | 类比                         |
| ------------------------ | ---------------------------------------------------- | ---------------------------- |
| **Retrieval（检索）**    | 从知识库中找到与问题最相关的文档片段                 | 去图书馆找书                 |
| **Augmentation（增强）** | 把检索到的文档片段拼入 Prompt，作为 LLM 的"参考材料" | 把书翻到相关章节，放在桌面上 |
| **Generation（生成）**   | LLM 基于"问题 + 参考材料"，生成最终答案              | 看着书回答问题               |

### 1.3 RAG 的两阶段流程

RAG 的完整流程分为**离线准备**和**在线问答**两个阶段：

```
════════════════════════════════════════════════
  离线阶段（提问前，一次性完成）
════════════════════════════════════════════════
  原始文档 → 分片（Chunking）→ Embedding 向量化 → 存入向量数据库
════════════════════════════════════════════════



════════════════════════════════════════════════
  在线阶段（每次提问，实时执行）
════════════════════════════════════════════════
  用户问题 → 向量化 → 向量库检索（召回）→ 重排序 → 拼入 Prompt → LLM 生成答案
════════════════════════════════════════════════
```

> **核心区别**：召回和重排的协作关系——召回快、粗、便宜（百万级→百级），重排慢、精、贵（百级→十级）。两者协作，既保证了速度，又保证了精度。

## 二、离线阶段：把知识"喂"给向量数据库

### 2.1 分片（Chunking）：RAG 的第一个工程决策

分片是 RAG 的起点，也是最容易被低估的环节。**分片策略直接决定了检索质量的上限。**

| 策略             | 做法                                                         | 优点                 | 缺点                             | 适用场景                         |
| ---------------- | ------------------------------------------------------------ | -------------------- | -------------------------------- | -------------------------------- |
| **固定长度分片** | 按固定 Token 数切分（如 512 Token/片）                       | 实现简单，性能稳定   | 可能切断语义，一句话被分到两片   | 通用场景、快速原型               |
| **递归字符分片** | 按 `\n\n` → `\n` → 句号 → 逗号 递归切分，尽量在语义边界处断开 | 兼顾效率和语义完整性 | 对 Markdown 等结构化文档效果一般 | 长文档（PDF、网页）              |
| **语义分片**     | 用 Embedding 模型检测段落主题变化，在语义边界处切分          | 语义完整性最高       | **需要逐段计算 Embedding 并对比相邻段相似度，长文档（万级 Token）分片成本极高；绝大多数企业生产环境不会全局语义分片**，更多作为小规模精选文档的补充方案 | 高质量要求场景、文档量可控的小规模知识库 |
| **结构化分片**   | 按 Markdown 标题、HTML 标签、PDF 章节等文档结构切分          | 充分利用文档结构信息 | 依赖文档格式，通用性差           | 结构化文档（技术文档、API 文档） |

**关键参数：Chunk Size 和 Overlap**

| 参数           | 含义                    | 调大                         | 调小                         |
| -------------- | ----------------------- | ---------------------------- | ---------------------------- |
| **Chunk Size** | 每片的大小（Token 数）  | 上下文更完整，但检索精度下降 | 检索更精准，但可能丢失上下文 |
| **Overlap**    | 相邻两片重叠的 Token 数 | 减少语义断裂，但增加存储     | 存储更省，但可能切断关键信息 |

**工程上常用的经验值**：Chunk Size = 512 Token，Overlap = 50 Token。这是 LangChain 等主流框架的默认值，经过了大量实践验证。

### 2.2 Embedding：把文本变成"语义坐标"

分片之后，每片文档都是一段自然语言文本。**计算机无法直接比较两段文本的"语义相似度"**——它需要把文本先转成数字。

#### Embedding 的本质

> **Embedding 就是把一段文本映射到一个高维向量空间中的一个点。语义相近的文本，在这个空间中的距离也相近。**

```
"今天天气怎么样" → Embedding → [0.12, -0.34, 0.78, ..., 0.05]  (1536维)
"今天气温多少度" → Embedding → [0.11, -0.32, 0.80, ..., 0.03]  (1536维)
                               ↑ 两条语义相近，向量距离很近（余弦相似度 ≈ 0.95）

"Python 怎么安装" → Embedding → [-0.45, 0.67, -0.12, ..., 0.88] (1536维)
                               ↑ 语义不同，向量距离很远（余弦相似度 ≈ 0.12）
```

#### 主流 Embedding 模型

| 模型                       | 厂商         | 维度 | 特点                         |
| -------------------------- | ------------ | ---- | ---------------------------- |
| **text-embedding-3-small** | OpenAI       | 1536 | 性价比高，通用场景首选       |
| **text-embedding-3-large** | OpenAI       | 3072 | 精度更高，成本也更高         |
| **bge-large-zh-v1.5**      | BAAI（智源） | 1024 | 中文效果最佳，开源可本地部署 |
| **m3e-base**               | 开源社区     | 768  | 中文轻量级，适合本地推理     |
| **Cohere Embed v3**        | Cohere       | 1024 | 支持多语言，压缩二进制嵌入   |

> **选型建议**：中文场景优先用 `bge-large-zh`，通用场景用 `text-embedding-3-small`，成本敏感场景用 `m3e-base` 本地部署。

#### 余弦相似度：衡量两个向量的"距离"

```python
# 余弦相似度：值越大，语义越相似
import numpy as np

def cosine_similarity(vec_a, vec_b):
    return np.dot(vec_a, vec_b) / (np.linalg.norm(vec_a) * np.linalg.norm(vec_b))

# 示例
weather_vec = [0.12, -0.34, 0.78, 0.05]    # "今天天气怎么样"
temp_vec    = [0.11, -0.32, 0.80, 0.03]    # "今天气温多少度"
python_vec  = [-0.45, 0.67, -0.12, 0.88]   # "Python 怎么安装"

print(cosine_similarity(weather_vec, temp_vec))   # 0.95 → 高度相似
print(cosine_similarity(weather_vec, python_vec)) # 0.12 → 不相似
```

### 2.3 向量数据库：RAG 的"存储引擎"

向量化之后，每片文档都变成了一个向量 + 原始文本。这些数据需要存在一个能**按向量相似度快速检索**的数据库中。

| 向量数据库                   | 类型            | 特点                                    | 适用场景                      |
| ---------------------------- | --------------- | --------------------------------------- | ----------------------------- |
| **Chroma**                   | 开源嵌入式      | 轻量、易用、Python 原生，适合快速原型   | 学习、POC、小规模项目         |
| **FAISS**                    | Meta 开源库     | 单机检索性能极强；支持手动序列化保存索引，但**无自动持久化、元数据管理、分布式能力**，一般不直接对外提供数据库服务 | 单机、高性能检索              |
| **Milvus**                   | 开源分布式      | 云原生、支持十亿级向量、分布式扩展      | 企业级生产环境                |
| **Pinecone**                 | 商业 SaaS       | 全托管、零运维、按量付费                | 不想自己管基础设施            |
| **PGVector**                 | PostgreSQL 插件 | 利用现有 PG 数据库，向量检索 + SQL 查询 | 已有 PostgreSQL 的场景        |
| **Weaviate**                 | 开源            | 自带向量化模块，支持 Hybrid Search      | 需要混合检索（向量 + 关键词） |
| **Elasticsearch + 向量插件** | 开源            | 全文检索 + 向量检索一体化               | 已有 ES 基础设施的场景        |

**ANN（近似最近邻）为什么必要？**

精确的最近邻搜索复杂度是 O(N×D)，N = 100 万条记录，D = 1536 维 → 精确搜索太慢。ANN 通过适度牺牲召回精度（精确搜索召回率 100%，ANN 通常可达 90%~98%），换取数十至上千倍的查询速度提升。

| ANN 算法           | 原理                                   | 特点                         |
| ------------------ | -------------------------------------- | ---------------------------- |
| **HNSW**           | 构建多层可导航小世界图，逐层搜索       | 查询快、精度高，但内存占用大 |
| **IVF**            | 先聚类再搜索，只在最近的中心点附近搜索 | 内存友好，适合大规模数据     |
| **PQ（乘积量化）** | 将高维向量压缩为短编码，压缩存储       | 极致压缩，但精度损失较多     |

## 三、在线阶段：从检索到生成的完整链路

### 3.1 召回（Retrieval）：粗筛百级候选人

用户问题来了之后，第一步是**召回**——从百万级向量中快速找到最相关的 Top 50-100 条。

```text
用户问题："Spring Boot 中如何配置 JWT 认证？"
    ↓
Embedding 向量化 → [0.23, -0.15, 0.78, ...]
    ↓
向量数据库 ANN 检索 → 找到 Top 50 条最相似的文档片段
    ↓
召回结果（50 条）→ 进入下一步重排
```

**混合召回：向量检索 + 关键词检索**

纯向量检索有一个容易被忽略的缺陷：**对精确匹配不敏感**。比如用户搜"v3.2.1 版本的变更日志"，向量检索会找到"版本更新说明"、"发版记录"等语义相近的文档——但"v3.2.1"这个精确版本号可能被淹没在语义相似度中。

**工程上通用的解法是混合召回**：向量检索 + BM25（关键词检索）各自召回 Top 50，然后合并去重，再送入重排。BM25 基于词频-逆文档频率，能精确命中包含特定关键词的文档，补上了向量检索"精确匹配弱"的短板。

```text
用户问："v3.2.1 版本的变更日志"
    ↓
向量检索：找到"版本更新说明"、"发版记录"等语义相近的文档（50 条）
BM25 检索：精确匹配"v3.2.1"字符串，命中包含该版本号的文档（50 条）
    ↓
合并去重 → 重排 → 最终 Top 3-5
```

> **合并方式**：注意 BM25 得分与向量余弦相似度值域不统一，不能直接加权相加。工程上主流采用 **RRF（倒数排名融合）** 方式合并两路结果——对每篇文档，取它在两路中的排名倒数之和作为融合分数，公式简洁且无需调参，再送入重排模型精排。

> **关键认知**：不是所有场景都需要混合召回。纯向量检索在语义理解型问题（如"怎么优化数据库性能"）上效果很好；混合召回在精确匹配型问题（如版本号、错误码、API 名称）上优势明显。**工程上建议默认开启混合召回，通过调整向量检索和关键词检索的权重来适配不同场景。**

### 3.2 重排（Reranking）：精筛十级最终结果

召回的结果是"粗筛"——用 Embedding 模型的余弦相似度排序，但 Embedding 模型的排序精度有限。**重排用更强的 CrossEncoder 模型，对召回结果做精细排序。**

| 维度       | 召回（Retrieval）                  | 重排（Reranking）                        |
| ---------- | ---------------------------------- | ---------------------------------------- |
| **模型**   | Bi-Encoder（Embedding 模型）       | CrossEncoder（交叉编码器）               |
| **速度**   | 毫秒级                             | 数十毫秒/条                              |
| **精度**   | 中等                               | 高                                       |
| **处理量** | 百万级 → 百级                      | 百级 → 十级                              |
| **原理**   | 问题和文档分别编码，再算余弦相似度 | 问题和文档拼接后一起编码，直接判断相关性 |

**为什么 CrossEncoder 更精准？**

- Bi-Encoder：问题 → 向量 A，文档 → 向量 B，然后算 A 和 B 的距离。问题和文档在编码时**互相看不到对方**。
- CrossEncoder：把"问题 + 文档"拼接成一段文本，一起编码。模型在编码时**同时看到了问题和文档**，能捕捉到更细粒度的交互关系。

```python
# 重排的典型实现
from sentence_transformers import CrossEncoder

reranker = CrossEncoder('BAAI/bge-reranker-large')
pairs = [[question, doc] for doc in retrieved_docs]
scores = reranker.predict(pairs)

# 按分数排序，取 Top 3-5
top_k = sorted(zip(scores, retrieved_docs), reverse=True)[:5]
```

### 3.3 生成（Generation）：LLM 基于参考材料输出

召回和重排之后，我们得到了 3-5 条最相关的文档片段。最后一步：**把这些问题和文档拼成 Prompt，送给 LLM。**

```text
System Prompt:
"你是一个专业的问答助手。请根据以下参考资料回答用户的问题。
参考资料的信息优先级高于你的内置知识，如果参考资料和你的记忆有冲突，以参考资料为准。
如果参考资料中没有相关信息，请明确说'我不确定'，不要编造。
参考资料：
---
{文档片段 1}
{文档片段 2}
{文档片段 3}
---
用户问题：{用户问题}"
```

**Prompt 模板设计的关键原则**：

| 原则                       | 说明                                    | 原因                                                     |
| -------------------------- | --------------------------------------- | -------------------------------------------------------- |
| **参考资料优先级高于内置知识** | 明确告知 LLM 以检索到的文档为准，而非依赖训练记忆 | **大量 RAG 效果差的根源：即使提供了文档，LLM 仍优先使用自身记忆**，需显式约束 |
| **明确告知资料来源**       | 在 Prompt 中标注"以下是参考资料"        | LLM 需要知道哪些是"事实"，哪些是"要求"                   |
| **要求引用来源**           | 让 LLM 在回答中标注每条信息来自哪个文档 | 可追溯、可验证，减少幻觉                                 |
| **兜底策略**               | 明确告知"不知道就说不知道"              | 防止 LLM 在参考资料不足时编造                            |
| **控制输出长度**           | 限制回答字数或结构                      | 防止 LLM 离题发挥                                        |

## 四、进阶 RAG 技术：从"能用"到"好用"

基础 RAG 在许多场景下效果不错，但遇到了新的问题：

| 问题                               | 表现                                      | 催生的技术      |
| ---------------------------------- | ----------------------------------------- | --------------- |
| 用户问题太短，检索效果差           | "这个怎么用？"→ 无法精准检索              | **HyDE**        |
| 不需要检索的时候也检索了           | 用户说"你好"，RAG 也去检索一遍            | **Self-RAG**    |
| 检索结果质量差，LLM 被迫用错误信息 | 检索到的文档不相关，但 LLM 还是用了       | **CRAG**        |
| 复杂问题需要多步推理               | "A 公司和 B 公司什么关系？"→ 需要多跳检索 | **Graph RAG**   |
| 需要 Agent 自主决策检索策略        | 不同问题需要不同的检索深度和来源          | **Agentic RAG** |

### 4.1 HyDE（假设文档嵌入）

**问题**：用户的自然语言问题，和知识库中的文档，在向量空间中的分布可能不一致。用户问"怎么解决内存泄漏"，但文档里写的是"内存管理最佳实践"——直接匹配效果差。

**HyDE 的解法**：**先让 LLM 生成一个"假设回答"，用这个假设回答去检索，而不是用原问题。**

```text
用户问题："怎么解决 Java 内存泄漏？"
    ↓
LLM 生成假设回答：
"Java 内存泄漏通常由长生命周期对象持有短生命周期对象的引用导致。
常见解决方案包括：使用弱引用、及时关闭资源、使用内存分析工具如 MAT 和 JProfiler..."
    ↓
用假设回答去检索 → 假设回答和文档都处于"文档空间"，匹配更精准
```

**为什么有效**：问题和文档在向量空间中的分布不同（问题短、文档长），但假设回答和文档在同一个分布中。**HyDE 本质上是把"问题向量"翻译成了"文档向量"，缩小了检索空间的不匹配。**

### 4.2 Self-RAG（自反思检索增强生成）

**问题**：基础 RAG 对每个问题都检索，但有些问题不需要检索（如"你好"、"1+1 等于几"），有些问题检索了也没用（检索结果质量差）。

**Self-RAG 的解法**：**让 LLM 自己在生成过程中判断：是否需要检索 → 检索结果是否相关 → 生成是否可靠。**

```text
Self-RAG 的四个反思标记：

① Retrieve（是否需要检索）：
   "你好" → 不需要检索 → 直接回答
   "最新的 Spring Boot 版本" → 需要检索 → 触发检索

② IsREL（检索结果是否相关）：
   检索到的文档和问题相关 → 使用
   检索到的文档和问题不相关 → 放弃，换关键词重新检索

③ IsSUP（生成是否被检索结果支撑）：
   回答中的每句话都能在检索结果中找到依据 → 通过
   回答中有编造的内容 → 标记，重新生成

④ IsUSE（生成的回答是否有用）：
   整体回答是否解决了用户的问题 → 最终评估
```

### 4.3 CRAG（纠正性 RAG）

**问题**：检索结果质量差怎么办？不相关、过时、来源不可靠……

**CRAG 的解法**：**对检索结果做质量评估，低质量则触发纠错机制。**

```text
检索结果 → 质量评估器
  ├── 高质量 → 直接使用
  ├── 模糊 → 本地知识库检索 + 联网搜索合并，并对合并结果做知识片段分解提纯（Decompose & Recompose），再送入 LLM
  └── 低质量 → 放弃本地检索，完全改为联网搜索
```

> CRAG 的核心创新在于"模糊"这个中间态：不是简单重写查询，而是**将本地知识库和联网搜索结果合并**，再通过知识片段分解提纯，从中提取有效信息重新组织，确保 LLM 接触到的始终是经过筛选的高质量素材。

### 4.4 Graph RAG（图谱 RAG）

**问题**：基础 RAG 一次检索只能回答一个问题。遇到需要多步推理的复杂问题时（如"A 公司的 CEO 是谁？他毕业于哪所大学？"），传统 RAG 配合多轮 Agent 也可以实现多跳检索，但效率低——每次跳转都需要一次完整的检索-生成循环，中间结果容易丢失，且多轮累积的上下文可能超出窗口限制。

> "A 公司的 CEO 是谁？他毕业于哪所大学？这所大学的校长是谁？"

**Graph RAG 的解法**：**把知识库从"文档片段"升级为"知识图谱"**——实体（人、公司、地点）是节点，关系（任职于、毕业于、位于）是边。

| 维度         | 传统 RAG             | Graph RAG          |
| ------------ | -------------------- | ------------------ |
| **知识表示** | 文档片段             | 实体 + 关系        |
| **检索方式** | 语义相似度           | 图谱遍历           |
| **多跳推理** | 可配合多轮 Agent 实现，但效率低、上下文易溢出 | 强，预先构建实体关系，沿图边遍历，减少多轮检索开销 |
| **适用场景** | 问答、摘要           | 关系推理、多步查询 |

### 4.5 Agentic RAG（智能体 RAG）

**问题**：不同问题需要不同的检索策略——简单问题查一次就够了，复杂问题需要多轮检索、多来源交叉验证。

**Agentic RAG 的解法**：**把 RAG 交给 Agent，让 Agent 自主决策"什么时候检索、检索什么、检索几次"。**

```text
用户："对比一下 Spring Boot 3.x 和 Quarkus 的性能"

Agent 的决策链：
  Thought: 这个问题需要多来源对比，先搜 Spring Boot 3.x 性能
  Action: 检索知识库"Spring Boot 3.x 性能基准"
  Observation: 找到了 3 篇相关文档
  
  Thought: 还需要 Quarkus 的性能数据
  Action: 检索知识库"Quarkus 性能基准"
  Observation: 找到了 2 篇相关文档
  
  Thought: 还需要两者的对比文章
  Action: 检索知识库"Spring Boot vs Quarkus 性能对比"
  Observation: 找到了 1 篇对比文章
  
  Thought: 信息够了，可以开始对比分析
  Final Answer: 基于 6 篇文档的综合对比分析...
```

## 五、实际项目中的 RAG 落地实践

理解了 RAG 的理论，我们选一个最具代表性的场景做深度剖析——**企业知识库问答**。这个场景覆盖了 RAG 最核心的工程挑战，也是 RAG 落地中最典型的案例。

### 5.1 企业知识库问答（智能客服）

#### 场景描述

企业有大量的产品文档、FAQ、内部规范，客服人员不可能全部记住。用户问一个问题，系统自动从知识库中检索相关文档，生成准确的回答。

**代表产品**：钉钉 AI 助理、飞书智能伙伴、即时设计 AI 助手

#### 为什么这个场景最能体现 RAG 的核心价值？

企业知识库问答是 RAG 最经典的落地场景，因为它**同时触及了 LLM 的三大硬伤**：

| LLM 硬伤     | 在企业知识库场景中的表现                     |
| ------------ | -------------------------------------------- |
| **知识截止** | 产品每周更新，LLM 训练数据里没有新功能的文档 |
| **幻觉**     | 用户问"这个功能怎么收费"，LLM 可能编一个价格 |
| **私有数据** | 企业内部规范、产品文档 LLM 不可能见过        |

**没有 RAG 时**：LLM 对产品功能的回答全靠"猜"，准确率可能不到 50%。**有了 RAG 后**：LLM 基于产品文档回答，准确率可以提升到 85% 以上。

#### 每个环节的工程决策

**1. 问题改写（Query Rewriting）—— 被低估的关键一步**

用户的问题往往是口语化的、不完整的。直接向量化检索效果很差：

```text
用户原始问题："这个功能怎么用？"
    ↓ 问题改写（用 LLM 或规则）
改写后："产品名称 + 功能名称 + 使用教程"
    ↓ 用改写后的问题做向量检索
检索结果精准度大幅提升
```

**为什么需要这一步？** 因为 Embedding 模型对短文本、口语化文本的编码效果远不如对完整、规范的文本。**问题改写本质上是把"用户语言"翻译成"检索语言"**。

**2. 混合召回 —— 向量检索 + BM25 关键词检索**

纯向量检索有一个致命缺陷：**对精确匹配不敏感**。

```text
用户问："v3.2.1 版本的变更日志"
向量检索：找到"版本更新说明"、"发版记录"等语义相近的文档
         → 但 v3.2.1 这个精确版本号可能被"淹没"在语义相似度中

BM25 检索：直接匹配"v3.2.1"字符串
         → 精确命中包含该版本号的文档
```

**混合召回的做法**：向量检索 + BM25 各自召回 Top 50，然后合并去重，再送入重排。这解决了"语义理解"和"精确匹配"不可兼得的问题。

**3. 元数据过滤 —— 缩小检索范围**

企业知识库往往有清晰的元数据结构（产品线、版本号、语言、文档类型）。在检索前先做元数据过滤，可以大幅提升召回精度：

```text
用户问："国际版 v2.0 的 API 文档"
    ↓
元数据过滤：product_line="国际版" AND version="v2.0" AND doc_type="API"
    ↓
在过滤后的子集中做向量检索
    ↓
召回精度远超全库检索
```

**4. 引用溯源 —— 幻觉的最后一道防线**

企业知识库场景对幻觉的容忍度很低。**引用溯源**是指在 LLM 回答时，要求它标注每条信息来源自哪个文档的哪个段落：

```text
LLM 输出：
"v3.2.1 版本新增了批量导入功能 [来源：产品更新日志 §3.2]，
支持 CSV 和 Excel 两种格式 [来源：批量导入功能文档 §2.1]。
注意：单次导入上限为 10000 条 [来源：系统限制说明 §1.3]。"
```

这样做的好处：

- 用户可以快速验证答案是否准确（点击来源链接查看原文）
- LLM 在要求引用时，编造内容的比例显著下降
- 如果某条信息在文档中找不到，LLM 会说"参考资料中没有相关信息"，而不是编造

**5. 增量索引 —— 文档更新如何同步？**

产品文档每周更新，RAG 知识库就面临同步更新的挑战。增量索引的流程：

```text
文档更新事件（Webhook / 定时扫描）
    ↓
对比新旧文档的 Hash 值 → 找到变更的文档
    ↓
只对变更的文档重新分片 + Embedding
	    ↓
	先写入新向量，验证生效后再删除旧向量；若采用物理删除，需预留版本回滚机制，优先考虑软删除标记方案
    ↓
总耗时：文档量 × 分片数 × Embedding 耗时
（1000 篇文档 × 平均 10 片 × 50ms/片 ≈ 500 秒 ≈ 8 分钟）
```
## 六、RAG 落地的核心工程挑战与应对策略

理论方案与项目架构介绍完毕，下面总结项目开发过程中高频遇到的工程难题与落地解法：

| 问题                                      | 解法                                                         |
| ----------------------------------------- | ------------------------------------------------------------ |
| **1. 分片大小怎么定？**                   | 512 Token 作为通用基准；技术文档、代码、API 文档可采用更小分片（256 Token）；论文、长篇报告等文本可放大至 1024 Token。分片同时配置重叠窗口，避免上下文被强行截断 |
| **2. 检索不到相关内容怎么办？** | **先判断库内是否真的存在答案**：① 改写用户问题（Query Rewriting）→ ② 切换检索策略（混合召回 / 关键词优先）→ ③ 若依然无相关结果，触发兜底（联网搜索 / 转人工）。**注意：不要单纯下调相似度阈值——如果库内根本不存在答案，放宽阈值只会捞进大量噪声文档，加重后续重排负担，更容易诱发幻觉。** |
| **3. 检索到的内容太多，超出上下文窗口？** | 召回 → 重排 → 取 Top 3-5 → 压缩文档片段（只取关键句）→ 注入上下文 |
| **4. 知识库更新了，怎么同步？**           | 增量索引：监听文档变更 → 重新分片 → 重新 Embedding → 更新向量数据库 |
| **5. 多模态（图片、表格）怎么办？**       | ① 图片用 OCR 提取文字 ② 表格用 Markdown 格式保留结构 ③ 或直接用多模态 Embedding 模型 |
| **6. RAG 回答质量怎么评估？**             | ① 忠实度（回答是否基于检索结果）② 相关性（回答是否切题）③ 完整性（是否覆盖了所有重要信息） |
| **7. 成本怎么控制？**                     | ① Embedding 用本地模型（m3e / bge）② 向量数据库用开源方案（Chroma / Milvus）③ 缓存高频问题的检索结果 |

## 七、核心要点速查

**要点 1：RAG 为什么存在？**

> LLM 有知识截止和幻觉两大硬伤。RAG 通过"先检索、再回答"的方式，让 LLM 基于外部知识库回答问题，而不是凭"记忆"编造。**但 RAG 只能缓解幻觉、不能根除**——即使上了 RAG，LLM 仍可能曲解正确文档（内在幻觉）或利用错误召回结果生成不实内容（外源幻觉）。正确认知：RAG 把幻觉率从 ~30% 降到 ~5%，残余幻觉需要引用溯源、兜底策略等机制兜底。

**要点 2：RAG 的两阶段流程是什么？**

> 离线阶段：原始文档 → 分片 → Embedding 向量化 → 存入向量数据库。在线阶段：用户问题 → 向量化 → 召回（粗筛 Top 50）→ 重排（精筛 Top 3-5）→ 拼入 Prompt → LLM 生成答案。

**要点 3：召回和重排的区别？**

> 召回用 Bi-Encoder（Embedding 模型），速度快、精度中等，处理百万级→百级；重排用 CrossEncoder，速度慢、精度高，处理百级→十级。两者协作，兼顾速度和精度。

**要点 4：四种分片策略怎么选？**

> 固定长度（通用场景）→ 递归字符（长文档）→ 语义分片（高质量要求）→ 结构化分片（Markdown/PDF）。工程上常用 Chunk Size = 512，Overlap = 50。

**要点 5：HyDE 和 Self-RAG 分别解决什么问题？**

> HyDE：先让 LLM 生成假设回答，用回答去检索，解决"问题→文档"向量空间不匹配。Self-RAG：让 LLM 自己判断是否需要检索、检索结果是否相关、生成是否可靠，避免不必要的检索。

**要点 6：Graph RAG 和 Agentic RAG 的适用场景？**

> Graph RAG：多跳推理（"A 公司和 B 公司什么关系？"），需要知识图谱。Agentic RAG：复杂任务，Agent 自主决策何时检索、检索什么、检索几次。

**要点 7：RAG 在真实项目中的核心挑战？**

> 分片策略（不同文档类型不同策略）、检索质量（召回 + 重排 + 兜底）、知识更新（增量索引）、幻觉控制（引用溯源 + 多层校验）、成本优化（本地模型 + 缓存）。

## 八、写在最后

RAG 是 AI 工程体系中**承上启下**的关键一环。

- **承上**：它缓解了 LLM 深度剖析一文中提出的"知识截止"和"幻觉"两大硬伤
- **启下**：它是 Agent 核心组件中"记忆模块"（尤其是向量记忆）的底层基础

理解了 RAG，你就明白了为什么 Agent 需要"记忆系统"——**不是 LLM 记不住，而是 LLM 需要一套"检索 + 增强"的工程机制来弥补架构层面的缺陷。**

从这个角度看，RAG 不是孤立的技术，而是整个 AI Agent 体系的"知识补给站"——有了它，Agent 才能从"凭记忆回答"升级为"查资料后回答"。
